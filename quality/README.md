# Verification and anomaly reports

The evidence behind the quality claims. What each gate checks, and what it does not, is explained in [../docs/QUALITY_GATES.md](../docs/QUALITY_GATES.md); these are the reports themselves, as produced by the pipeline for the released graphs.

| File pattern | Gate | What to look for |
| --- | --- | --- |
| `osm_census_<city>.md` | OSM ingestion completeness census | the source-against-graph table (must match per OSM kind), the per-feature fidelity findings (must be "None"), and the placement, indexing, and provenance gates (all violations must be 0) |
| `stats_control_<city>.md` | per-city statistical and anomaly control | severity-ranked findings, the decisions taken, and the cross-checks; in particular building loss, which is zero for every city |
| `cross_source_conflict_<city>.md` | cross-source conflict measurement | how many buildings carry a value from more than one source for the same attribute, and how far apart those values are |
| `roundtrip_census.md` | lossless CityGML round-trip census | per level of detail and per thematic module: source instances against instances missing from the export, which is zero throughout |
| `duplicate_ids_traceability.md` | identity resolution | which features were deduplicated, which were split onto synthesized ids, and how the original `gml:id` remains recoverable |
| `disk_footprint.md` | storage accounting | store size per city and per ingestion stage, measured additively because Neo4j does not shrink store files on delete |

## Reading a report honestly

Each `stats_control_<city>.md` lists flags that were **investigated and dismissed**, with the reason. They are kept in the reports rather than filtered out, because a reviewer should see what the gate raised. The recurring ones:

- **`ID_COLLAPSE` false positives.** The gate flags buildings whose node fan-out is unusually large, since that is the signature of two features collapsing into one id. On Hamburg (4), Zurich (3), New York (51), and Tokyo (273) these turned out to be genuinely large single buildings, verified against the source, whose `gml:id` is unique there. One example: a New York building with 3,433 boundary surfaces and no parts.
- **`OSM_HIGH_ORPHAN_RATE`.** Up to 94.5 % on Zurich. Expected: the OSM extract is clipped to the dataset bounding box, which covers considerably more area than a canton-wide tile scatter of authoritative buildings, and unmatched OSM features are kept deliberately as net-new knowledge.
- **`SPATIAL_OUTLIER`.** On Hamburg, 92 features at the extremes of a bounding box that spans a federal state. The city's own extent, not a coordinate error.
- **`HEIGHT_SENTINEL`, `CRS_RANGE_MISMATCH`** on Tokyo. The PLATEAU `-9999` height and `9999` storey sentinels, preserved verbatim, and the expected consequence of a reprojected source.
- **`NO_GEOMETRY`** on Zurich (5). Placeholder features in the source with no geometry, which is why those five deduplicate rather than split.
- **`OGRINFO_FAILED`.** An optional source-profiling step that needs the GDAL CLI, which was unavailable in some runs. It affects the report's source-side profile only, never the graph or any other gate.

Script paths named inside these reports (`eval/...`, `bench/...`) refer to the [pykci](https://github.com/hcu-cml/pykci) construction pipeline, which is where the gates run.

## Reproducing

Every report is regenerated by a scripted stage, in the order given in [../docs/REPRODUCE.md](../docs/REPRODUCE.md) section C. The cross-source conflict analysis is the one you can re-run directly against a restored graph without the source files:

```bash
python tools/osm_citygml_conflict_analysis.py --dataset hamburg_citygml2_lod2_2025.gml
```
